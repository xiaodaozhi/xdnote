# D1：Qt 文档与窗口技术试验

本目录是可复现的技术验证代码，不是 xdnote 产品或可交互设计原型。它验证 Qt 候选方案的部分关键行为，不预先决定最终界面框架、解析器、文件模型或发行工具链。

## 试验覆盖

| 验证点 | 方法和边界 |
| --- | --- |
| 同一文档跨窗口 | 两个 Qt Quick `TextEdit` 接入同一 `QTextDocument`，在隐藏的独立窗口与工作区窗口间接管，核对正向／反向选区、文本及撤销重做 |
| 单控件跨窗口候选 | 将同一个带辅助功能角色的编辑控件移动到另一个窗口，不替换其文档；核对选区、撤销、辅助功能文本、原窗口销毁和合成组合输入期间拒绝迁移 |
| 输入法组合 | 发送合成的 `QInputMethodEvent`，组合期间拒绝接管，提交后继续；不代表真实中文输入法已验收 |
| 辅助功能接口 | 对照未标注的 `TextEdit`、显式声明可编辑文本角色的样例和 `QPlainTextEdit`，检查 Qt 辅助功能文本、整段与范围写入及撤销；不代表平台辅助技术已验收 |
| Windows UI Automation 对照 | 由独立客户端访问自己父进程创建的受控窗口，检查只读／可编辑状态的值写入、文本和撤销；仅 Windows 原生窗口测试运行，离屏 CI 不执行该路径 |
| 真实桌面手动试验 | 可运行双窗口测试工具，使用同一接管函数观察真实输入法、选区及撤销；工具不会读取或保存文件，结果需逐平台实际记录 |
| Markdown | 对标题、任务列表、表格、围栏代码、原始 HTML 和图片请求做有限样本检查，预览阶段不复用源文的撤销栈 |
| Markdown 语义与链接边界 | 以自建语料核对标题、强调、引用、有序列表和围栏代码；检查预览不重置源文撤销，并观察解析后的链接协议仍需调用方审核 |
| 资源访问 | 预览文档覆盖资源加载器，测试中一律返回占位图，不访问本地或网络资源；真实图片服务尚未实现 |
| 图片引用边界候选 | 对相对路径、编码、父目录、Windows 特殊名称等做保守的词法对照；以自建符号链接展示仅靠词法检查无法限制实际访问 |
| Windows 目录连接反例 | 仅在自建夹具内建立目录连接，检查最终文件使用 `FILE_FLAG_OPEN_REPARSE_POINT` 时是否仍会经过中间连接；无法创建时明确跳过 |
| 文件保存 | 使用自建临时文件检查 UTF-8 BOM、CRLF、无断行空格、外部修改、目标删除与保存期间继续编辑 |
| 保存边界反例 | 用自建文件复现同内容替换、最终检查后外部修改以及 U+2029 文本信息丢失；这些断言记录候选方案的缺陷，不是产品预期 |
| Windows 文件共享失败 | 用自建文件的受控句柄分别阻止基线读取和目标替换，核对失败阶段、原字节、未保存状态与释放后的重试 |
| 跨进程读取与替换 | 子进程持有 Qt 或原生只读句柄，分别检查保存结果、旧句柄内容与冲突；Windows 另行对照两种替换原语及其原生错误码 |
| 文件身份候选 | 持有自建文件句柄，比较 Windows 卷序列号与 128 位文件 ID、Unix 设备号与 inode；检查硬链接和同内容替换，Unix 同时检查最终路径符号链接拒绝 |
| 保留被替换文件的候选 | 自建文件上使用 Windows `ReplaceFileW` 备份、macOS `RENAME_SWAP` 或 Linux `RENAME_EXCHANGE`，由独立子进程在替换前／后通过已打开的句柄写入并检查内容 |
| 基准 | 自生成 10 KiB、1 MiB、10 MiB Markdown，单次测量隐藏窗口、读取、文本插入、解析、排版和进程内存 |

Qt Quick 允许调用方将 `QTextDocument` 绑定到 `TextEdit`，并由调用方持有文档；详见 [Qt 6.8 QQuickTextDocument](https://doc.qt.io/qt-6.8/qquicktextdocument.html#setTextDocument)。Qt 的 `toPlainText()` 会转换不换行空格等字符，因此试验读取 `toRawText()` 并显式处理内部段落分隔符，见 [Qt 6.8 QTextDocument](https://doc.qt.io/qt-6.8/qtextdocument.html#toPlainText)。

本地进程通信测试在 Unix 下使用 `/tmp` 中新建的私有短目录，避免系统临时路径与套接字名合起来超过平台长度限制；Windows 使用唯一命名管道。测试仍验证真实子进程的请求与回复，不代表产品进程通信方案已确定。

## 重要限制

- 使用 `QSaveFile` 同目录暂存且关闭直接覆盖回退；两次比较目标字节能发现测试中注入的变化，但最后一次检查到提交之间仍有跨进程竞争。相同字节的文件替换、系统文件 ID、链接／重解析点、权限和网络卷尚未解决，不能用于真实用户文件保存。参见 [Qt 6.8 QSaveFile](https://doc.qt.io/qt-6.8/qsavefile.html)。
- 打开时拒绝混合换行、非 UTF-8 和源文已有的 U+2028／U+2029；编辑过程中 U+2028 拒绝保存。Qt 内部普通段落也使用 U+2029，因此编辑过程中插入字面 U+2029 尚不能和普通换行区分，这是待决的文本保真问题。
- `MarkdownNoHTML` 和占位资源加载只覆盖当前实验路径与样本；未完成对完整方言、嵌入对象、实际本地图片、链接协议、复杂文档及渲染资源上限的安全／兼容验收。
- 图片引用候选只解析相对 URL 并返回一次解码后的路径分量，拒绝无效 UTF-8、父目录、绝对地址和一组跨平台不安全名称；它不打开图片，也不代表产品已确定这些兼容性限制。调用方不能再次将分量当作 URL 解码。自建 POSIX 符号链接和 Windows 目录连接反例说明词法检查无法确保文件仍在文档目录内；Windows 对最终文件使用 `FILE_FLAG_OPEN_REPARSE_POINT` 仍可能经过中间目录连接，本机 Qt 的 `canonicalFilePath()` 在该样例中也未解析这个中间连接。其他重解析点、目录句柄、路径替换竞争、硬链接、图片解码和资源上限仍待验证，不能将候选结果当作读取授权。
- 当前 Qt 解析样例会将 `javascript:` 等不可信链接保留在文档的链接属性中；本实验不激活链接。产品必须在用户主动操作时另行校验并限制协议，不能把“禁止 HTML”和资源占位视为链接安全策略。
- 该试验的未标注 `TextEdit` 未暴露可查询的 Qt 辅助功能接口；显式声明角色的样例可通过文本接口读取内容并通过整段值替换，但没有单独的可编辑文本接口。在该单视图样例中，直接调用整段值替换会改变文档，即使控件报告只读，并会清除原撤销栈。此结果针对当前测试和 Qt 版本，不表示屏幕阅读器一定执行此调用，也不等于选区、变更通知或平台行为通过；产品需要单独处理辅助功能写入与文档会话的边界，见 [Issue #22](https://github.com/xiaodaozhi/xdnote/issues/22)。
- 另一组直接调用 Qt 接口的 `QPlainTextEdit` 对照中，只读时整段值写入不改变文本，但可编辑文本接口的插入、删除和范围替换仍会修改只读文档；在可编辑状态下整段值替换清除撤销记录，而范围替换在当前样例中分为删除和插入两个撤销步骤。这些是候选控件的负面观察，不是期望的产品行为，也不证明实际辅助技术会使用上述接口。
- Windows 原生窗口的受控 UI Automation 客户端对照中，只读样例的值写入返回失败，文本和撤销保留；可编辑样例的值写入成功但清除已有撤销记录。该客户端只访问父测试进程的指定窗口，测试窗口不接收焦点且放到屏幕外；结果限于实际测试的 Qt 与 Windows 环境，不代表所有辅助技术或平台行为。Qt 直接接口的只读问题仍存在，也未定位只读请求由哪一层拒绝。
- 已创建辅助功能接口后替换 Qt Quick 文档，自动试验观察到旧文档被销毁而接口对象仍被缓存。Windows Qt 6.8.2 的独立进程试验中，之后读取该接口的字符数发生访问异常；安全自动测试只检查上述前置条件，不故意执行可能崩溃的读取。原因、其他 Qt 版本与平台范围及处理方案仍待研究，见 [Issue #21](https://github.com/xiaodaozhi/xdnote/issues/21)。
- 单控件迁移是另一项受限候选，试验保持同一编辑器和文档，不证明重绑定问题已经修复。只测试一个编辑视图；真实窗口激活与焦点、布局、拖放、多个可见视图、辅助技术和各平台输入法仍需验证。控件需由比窗口更长寿命的对象持有；辅助功能写入的只读和撤销问题仍未解决。
- 保存边界反例证明这些具体场景下的候选实现不足；产品方案须另外解决文件身份、条件提交和文本保真问题，不应保留反例中发生的覆盖或字符归一化行为。后续研究见 [Issue #9](https://github.com/xiaodaozhi/xdnote/issues/9)。
- 文件身份探针只比较当前持有的文件句柄；不进入 `SpikeFile` 保存路径，也不保证路径持续指向同一对象。文件 ID 在不同文件系统可能不可用、变化或被复用；探针遇到无法取得身份时失败，不退化为路径或字节比较。最终路径的符号链接／重解析点按平台拒绝，父目录中的链接、Windows 重解析点的实际创建、网络卷和竞争仍未验证。
- 保留被替换文件的候选在替换后才可检查原内容；目标路径已经发生变化。原有文件句柄可能继续修改被替换的对象，故留存文件也不天然是不可变快照。不同平台失败状态、权限／元数据、持久化、链接及文件系统支持尚需验证；试验不接入保存路径，也不允许自动退回会丢失内容的替换方式。
- Windows 自建文件试验曾偶发“拒绝访问”，根因未确定，见 [Issue #26](https://github.com/xiaodaozhi/xdnote/issues/26)。保存试验记录基线读取、暂存和提交阶段，以及 `QSaveFile` 暴露的 Qt 文件错误；受控句柄能产生类似错误，不代表证明了偶发故障的原因。
- 当前 Windows 测试中，另一个进程持有只读句柄时，`QSaveFile` 的替换可能失败；即使该句柄允许删除共享，独立的 `MoveFileExW` 对照仍失败，而 `ReplaceFileW` 在此场景可保留旧对象。原生错误码只属于测试中紧随失败取得的独立原生调用，不能当作 `QSaveFile` 的原始错误码。不同文件系统、句柄类型和偶发失败的根因仍需核验，这些结果不构成安全的条件提交方案。
- 没有注册系统文件关联，也未验证操作系统双击、屏幕阅读器、原生菜单和真实桌面视觉。macOS、Linux 的真实桌面与输入法仍待验证；跨平台离屏 CI 或隐藏窗口创建成功不等于这些场景通过。
- 基准是单次合成样本，非真实键盘延迟、首次显示或产品性能结论；不使用共享机器的一次数字确定性能上限。

## 构建与运行

要求 Qt 6.8 或更新版本的 Core、Gui、Network、Qml、Quick、Test、Widgets 开发组件，以及 CMake、Ninja 和对应平台编译器。Qt 版本限制只适用于本试验；最终工具链尚未决定。需要能找到 Qt 动态库、平台插件和 QML 模块。

Windows 在 x64 MSVC 开发环境中执行：

```powershell
$xdnoteQtPrefix = 'C:\path\to\Qt\6.8.x\msvc2022_64'
pwsh -NoProfile -File experiments/qt-document-spike/run-windows.ps1 `
  -QtPrefix $xdnoteQtPrefix -NativeWindowTests -Benchmarks
```

若 CMake 或 Ninja 未在 PATH，可通过 `-CMakePath`、`-NinjaPath` 传入已有工具的绝对路径。脚本不会下载安装工具。更换 SDK 或编译器时传入不同的 `-BuildName`，避免复用旧 CMake 缓存。脚本在当前进程临时设置 Qt 路径和项目内的 `build/temp`，结束时恢复原环境；构建与报告位于忽略的 `build/`。MSVC 临时目录应使用该编译器能够处理的路径；本机遇到中文临时目录时使用项目内纯英文路径。

其他平台可在已配置 Qt 环境后使用常规 CMake 流程：

```sh
cmake -S experiments/qt-document-spike -B build/qt-document-spike \
  -DCMAKE_PREFIX_PATH=/path/to/qt -DCMAKE_BUILD_TYPE=Release
cmake --build build/qt-document-spike
ctest --test-dir build/qt-document-spike --output-on-failure
```

这条 CTest 路径运行离屏用例。三平台 CI 的结果见对应运行记录；离屏结果不能代替真实桌面测试。

## 双窗口手动接管试验

这是一段独立的技术验证，不是产品界面。工具只在内存中创建测试文字，不读取或保存用户文件；请勿输入需要保留的内容。两个窗口共享一个文档，仅当前窗口可编辑。窗口上的组合状态反映 Qt 在该窗口观察到的输入法状态；状态和接管结果显示在窗口中，不会自动形成验收记录。

Windows 使用上述脚本时加入 `-ManualHandoff`，自动检查结束后打开两个试验窗口；关闭两个窗口后脚本结束。例如：

```powershell
pwsh -NoProfile -File experiments/qt-document-spike/run-windows.ps1 `
  -QtPrefix $xdnoteQtPrefix -ManualHandoff
```

macOS 或 Linux 完成上述 CMake 构建后，在已配置 Qt 动态库、平台插件和 QML 模块的真实桌面环境运行 `build/qt-document-spike/qt_document_handoff_manual`。不要设置离屏平台变量后声称验证了真实输入法。

每个平台记录操作系统、Qt 版本、输入法名称、窗口系统与实际结果；测试以下步骤，并记录失败、跳过和观察：

1. 在当前窗口输入中文并提交，尝试正向和反向选择部分文字，分别用 F8 或按钮接管。检查目标窗口的文字、选区方向与光标，并在目标窗口撤销、重做；再接管回原窗口重复。非活动窗口应保持只读。
2. 开始中文输入但暂不提交，确认窗口显示“输入法组合中：是”，再尝试 F8 或接管按钮。只有接管请求到达工具时仍处于组合状态，才能观察拒绝；若输入法拦截 F8，或点击使组合先提交／取消，应如实记录，不能将其计作组合中拒绝通过。
3. 提交或取消组合后重试接管，检查已有文字、选区和撤销栈；同时检查无选区光标、空文档和多次往返。关闭试验窗口结束，不将结果当作产品或视觉验收。

`qt_document_handoff_smoke` 检查离屏加载、选区／撤销接管及合成输入法组合期间的接管，不验证操作系统输入法或真实桌面交互。人工结果和环境应记录在对应 Issue 或 PR，而不是将单次结果写成普遍平台结论。

## 证据

Windows 脚本每次创建新的 `build/qt-document-spike/runs/<随机标识>/`，保存源码 SHA-256、配置／构建日志、QtTest 报告和可选基准 JSON。源码在一次运行中发生变化会使脚本失败。自动测试文件只创建在已核验的构建目录子目录，测试只清理其独立的临时目录。

结果应结合工具链、平台、插件、样本和实际报告解读。测试数包含 QtTest 初始化和清理项；离屏、隐藏原生窗口、真实桌面与人工验收是不同范围。
