# 交互规格

本文规定首版文档和窗口行为。界面布局参考[当前原稿](../../design/hifi/README.md)，精确尺寸见[视觉参数](../visual/tokens.json)。

## 统一打开入口

系统文件关联、命令行文件参数、系统文件打开事件、应用内选择、最近文件和拖入文件都转换为 `OpenIntent`，不各自实现一套会话逻辑。多个路径按输入顺序接收，最后一个成功打开的文档获得焦点；单项失败不阻止其他项，失败有对应文件的明确反馈。

| 输入 | 默认结果 |
| --- | --- |
| 双击 `.md`／`.markdown` | 独立文件窗口，初始阅读模式 |
| 工作区文件树、目录内导航、标签栏加号选择的目录内文件 | 当前工作区标签页 |
| 菜单「打开文件」、对应快捷键、欢迎页打开文件 | 新独立窗口；不受工作区标签偏好影响 |
| 最近／收藏、标签栏加号或拖入工作区的目录外文件 | 独立文件窗口；不在工作区添加标签 |
| 工作区内文档链接 | 当前工作区标签页并按需定位片段；已有会话仍激活所属窗口 |
| 独立窗口中的相对文档链接 | 独立文件窗口；不隐式导入父目录或工作区 |
| 拖入某个工作区或独立窗口 | 先明确目标窗口意图，再进入相同去重与校验流程 |
| 同一文件已打开 | 激活已有会话及所属窗口，不再次读取以覆盖未保存内容 |
| 打开一个目录 | 仅作为用户主动选择的工作区，不由双击单个文件隐式触发 |

外部打开的目标和独立窗口初始模式可在[设置](settings.md)调整，只影响后续新会话，不迁移已经打开的窗口。`workspace-tab` 仅用于已经显式打开且包含目标文件的工作区；无匹配工作区或尚未选择目录时使用独立窗口，不为单文件创建空工作区或隐式授权父目录。所有新增工作区打开和异步完成均复核目录范围，路径相同前缀、`..` 和链接目录不视为目录内文件。

## 文档身份与窗口

工作区欢迎页提供「打开文件」「打开文件夹」「新建文档」，布局遵循[原稿对应规范](../visual/workspace-welcome.md)。新建文档进入未命名的独立编辑窗口，空白初态不标记为修改，首次保存选择位置；输入后执行同一未保存关闭保护，不将临时存储路径显示为真实保存位置。最近文档使用统一打开路由和已有唯一会话。

应用以稳定的 `DocumentId` 识别文档，窗口只是会话的承载者。窗口重排、切换视图、修改配色不会新建编辑缓冲区或重置撤销栈。首版同一文件只有一个可编辑会话，不提供互相独立的多个编辑副本。

「在工作区打开」的行为：

1. 找到已经显式选择且包含当前文件的工作区，将会话移入其中的标签页；没有匹配目录或目标不包含文件时，提示先打开所属工作区，保留独立窗口，不隐式选择父目录。
2. 保留未保存文本、编码、换行、选区、撤销栈和文档身份，不以重新读取磁盘替代迁移。
3. 完成接管后再关闭原独立承载窗口；接管失败时原窗口继续保留。
4. 不移动源文件，不自动导入父目录，也不把打开一个文件扩大为任意目录访问。

旧会话记录中的目录外文件恢复到独立窗口；未保存草稿恢复为独立副本，另存为确定真实位置后才允许接管。恢复不修改原文件或重置打开偏好。已经打开的文件继续复用其唯一会话与所属容器，不因新入口创建第二个缓冲区。

## 视图与导航

- 工作区的编辑、双栏、阅读共享同一缓冲区；独立窗口仅展示阅读或编辑中的一个。
- 阅读模式中的任务框不响应修改，链接由用户主动点击。编辑模式通过源文改变任务状态。
- 双栏自动按当前版本的标题／段落范围关联两侧滚动，在区间内按实际布局近似定位，不用整个文档的滚动百分比代替映射。重排、隐藏和正文更新时停用旧映射，不改变焦点、光标、选区或正文；实现边界与自动化入口见[段落映射滚动](../engineering/scroll-synchronization.md)，真实滚动手感单独验收。
- 侧栏可收起，窄窗口优先保留正文、模式切换和保存入口。菜单处理溢出，不缩小文字来塞入工具栏。
- 独立窗口标题栏显示文件名及未保存标记，父路径显示在下方工具栏的面包屑位置；图标按钮「在工作区打开」保留可读名称。长路径省略时提供完整可访问名称及查看位置入口。

## 窗口跨屏与恢复

普通窗口从高缩放显示器拖到低缩放显示器时保持逻辑客户区；目标空间不足则按[窗口几何契约](../engineering/window-geometry.md)收敛并使用共享紧凑布局，不放大窗口或把必要操作留在屏幕外。只移动不改变源文、字号偏好、选区或撤销。往返、主题变化与重复缩放通知不累计改变正常尺寸。

拖动、拖边、最大化、贴靠及全屏使用平台约定。用户主动调整与临时屏幕适配分别处理，恢复时重新核验当前屏幕与可用区域；显示器断连不留下无法到达的确认窗口。平台不允许精确设置窗口位置时遵循其安置规则，不宣称已恢复到某个全局坐标。

## 文档状态

以下维度独立表达，避免把阅读模式当作已保存，把只读权限当作编辑偏好。

| 维度 | 取值与规则 |
| --- | --- |
| 加载 | opening、ready、error，失败时保留可关闭的明确错误页 |
| 修改 | clean、dirty，比较当前缓冲版本与最后确认保存版本 |
| 保存 | idle、saving、conflict、error，不覆盖加载／修改的真实状态 |
| 权限 | writable、read-only，实际不可写时给出原因与另存为入口 |
| 视图 | source、split、reading，独立窗口不使用 split |

状态栏仅在原文件提交成功后显示「已保存」。保存期间显示「保存中」，失败显示「保存失败」及重试入口，源文仍可复制或另存为。

## 保存与外部修改

1. 手动保存、自动保存与另存为使用同一个保存服务，按文档串行提交，冻结本次文本版本、目标和源文件基线。
2. 对已有文件，保留编码与换行；在同目录准备临时文件，完成写入与必要刷新后再提交，不先截断原文件。
3. 提交前检查源文件是否被外部修改、替换或删除。发现冲突时暂停自动写入，提供「保留当前编辑」「重新载入磁盘版本」「另存为」等明确选择；载入导致放弃编辑时再次确认。
4. 写入后若用户已继续输入，仅将本次快照记为已保存版本，当前文档仍为 dirty。过期保存回执不能清除新修改标记。
5. 提交前失败保留原文件和内存修改；提交之后发生刷新或回执异常时核对实际内容，展示结果不确定，不能声称原文件必然未变化。平台提交与竞争边界见[技术架构](../engineering/architecture.md)。

外部变化监测到 clean 文档变化时，提示可重新载入并保留阅读位置；dirty 文档不自动覆盖缓冲区。删除、权限变化、网络卷断开都进入可理解的失败或冲突状态，而非创建新文件假装保存成功。

新建文档首次保存由系统选择器确认位置和文件名。仅阅读文件、改变设置或打开工作区不会创建旁置恢复文件。崩溃恢复草稿属于后续独立设计，不作为当前关闭保护的前提。

多个硬链接指向同一文件时采用另存为保护，保持原文件与其他链接不变，不通过原子替换悄悄拆开它们的内容关系。提示用户选择其他位置，读取与打开去重仍按文件身份处理。首轮文件原型的严格 UTF-8、容量、普通文件范围和异常恢复副本规则见[保存闭环](../engineering/file-save-workflow.md)；这些限制须在失败反馈中明确，不静默转码或丢弃内容。

## 工作区图片、链接与文件移动

按[工作区资源规格](workspace-resources.md)，新增受管图片默认集中于工作区 `assets/images/`，引用始终相对 Markdown 文件目录。先核验并提交图片，再通过会话插入引用；撤销或删除正文引用不自动删除磁盘资源。未命名文档先确定保存位置，打开工作区不预创建资源目录。

图片和文档链接共用带版本的引用索引，区分实际缺失、不可读、受阻和未完成扫描。工作区内 Markdown 链接通过统一打开路由复用会话，标题定位针对当前正文；文件外部目标和系统协议须另行校验，不由预览直接访问。

应用内移动／重命名之前展示影响计划，同时包含指向目标的入站引用和被移动文档自己的出站相对引用。确认后重新核验，打开文档通过已有会话更新并保留 dirty 状态，未打开文件通过统一保存服务写入。多文件部分成功须逐项反馈，不能冒充整体原子提交；外部改名只诊断并提供确认后的修复，不静默批改。

## 关闭、批量关闭与退出

| 状态 | 关闭行为 |
| --- | --- |
| clean | 直接关闭对应视图并释放会话 |
| dirty | 提供「保存」「不保存」「取消」；关闭提示本身等同取消 |
| saving | 等待实际终态或取消关闭，不强行销毁缓冲区 |
| conflict／save error | 保留修改，提供解决冲突、另存为或明确放弃，不能默认为已保存 |

关闭其他标签只影响所属窗口，命令绑定稳定文档身份，不能随标签重排误关其他文档。退出先处理所有未保存文档，任何取消都终止退出；已完成的保存继续有效，尚未明确放弃的缓冲区不提前销毁。

托盘常驻与关闭到后台不列入首版要求。平台菜单和应用生命周期必须经过原生验证，并遵守本产品的文档关闭保护。

## 键盘与可访问性

控件的焦点外框遵守[控件交互与焦点显示](control-interactions.md)：常规指针交互不显示 outline，仅 Tab／Shift+Tab 导航需要时显示；激活、取消、指针交互或失焦后隐藏，逻辑焦点与文本光标独立保留。

常见保存、新建、打开、关闭、撤销／重做使用平台约定快捷键，Windows／Linux 的 Ctrl 与 macOS 的 Command 对应由平台适配处理。设置与模式切换均可键盘到达，所有图标动作具有可读名称，焦点离开菜单后回到调用控件。

主题、配色、分段控件保持单选语义；鼠标、键盘和辅助功能动作提交同一选择意图。不能只改变控件的勾选图形而不更新文档、主题或设置模型。
