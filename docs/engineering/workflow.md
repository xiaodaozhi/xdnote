# 产研与 GitHub 协作流程

## 任务来源与分流

需求、Bug、视觉设计和技术研究统一在 GitHub Issues 跟踪；先搜索已有任务，避免重复。Issue 记录问题或场景、范围、可验证的验收、关联规格、依赖与阻塞。较大工作可由父任务关联可独立验收的子任务。没有真实缺陷证据时使用研究任务，不虚构 Bug。

每个 Issue 选择一个 `type:`，分流时选择一个 `priority:` 和一个 `status:`，必要时可有多个 `area:`。优先级 P0 表示阻塞关键可行性或数据安全，P1 表示当前阶段核心能力，P2 表示不阻塞当前阶段的改进。状态依次使用 `needs-triage`、`ready`、`in-progress` 或 `blocked`；阻塞时记录原因和恢复条件。Milestone 对应 [D0–D5 阶段](../planning/roadmap.md)，不把里程碑当作发布日期承诺。

产品／视觉文档只维护当前规则与决策；单次进度、PR、实际检查和结论记录在 Issue、PR 或 CI 运行中。研发决策写清备选、依据与限制，不把参考项目的技术路线直接当作本产品的决定。

## 实施、评审与合并

1. 范围和验收足够清晰后，从最新 `main` 创建带 Issue 编号的短期分支，开始实施时更新状态。
2. 一个 PR 保持可审查范围；说明行为变化、受影响的规范或设计、测试环境及实际结果。设计图先展示并按要求取得验收，不从图片推断应用能力。
3. 按风险执行适用验证，分别记录文档／素材检查、技术试验、产品行为、真实平台与人工视觉。失败、缺失、取消或旧提交的 CI 不算当前 head 通过。
4. 当前 head 检查、必要审查和本次范围验收均完成后，合并至 `main`。全部 Issue 验收满足才用 `Closes` 或关闭；部分完成使用 `Refs` 并保留未完成项。
5. 核对合并提交及 Issue 状态，只清理由本次工作创建且已合并的临时分支／临时数据；有未合并工作或不确定归属时保留。工作区允许时快进同步本地 `main`。

已授权的开发与修复默认包括推送任务分支、创建 PR 及通过门槛后的合并，无需逐步提醒；用户指定草稿、只提交、暂不合并或对设计提出修改时遵守指定边界。单维护者可以记录自审，但不能把自审冒充独立审查。原生或人工验收有待外部条件时，Issue 继续开放并明确原因。

## 当前 CI 与边界

`Design and repository checks` 在 Windows、macOS、Linux 上安装锁定的 Node 开发依赖，检查当前设计材料、链接、JSON、图片身份、参考切片和 Git 索引卫生。`Qt document experiment` 读取统一依赖清单的 Qt 6.8.2，在三个平台配置、编译并运行现有 Qt 文档实验的离屏 CTest，并在失败时输出首次文档测试报告；它与正式桌面使用独立产物，实验通过不等于产品验收。两者均在 main push、PR 和手动触发，使用只读仓库权限；实际结论以对应提交的 Actions 运行为准。

`Scintilla buffer experiment` 在相关实验或工作流变化时以及手动触发时运行；它在三平台显式下载并核验固定摘要的试验源码，分别测试核心文本缓冲区、Qt 控件的离屏文档接管与合成输入法事件，以及 Qt 辅助功能接口对照。Scintilla 已列为优先实施路线，但该工作流不验证真实输入法、屏幕阅读器或具体 Qt 承载，不代表编辑器准入完成，也不与其他 PR 的必需检查混为一谈。

`Markdown parser experiment` 在解析试验、共享语料或其工作流变化时以及手动触发时运行；它在三平台使用固定 Rust 试验版本显式下载锁定依赖，再离线检查解析事件、源文偏移、不可信内容，以及有限子进程夹具的过期结果与取消控制点，并测量自生成样本的解析时间。pulldown-cmark 路线已按架构确认，这个试验仍不验证解析过程中的实际取消、预览、资源授权或产品性能，也不锁定正式产品版本。

`Desktop admission` 使用[统一入口](developer-build.md)显式准备固定 SDK 和源码依赖，再离线构建桌面基础模块与 Rust 服务，运行会话、编辑适配、基础辅助功能、混合控件承载及受限预览测试。默认矩阵包含 Windows 2022、macOS 双架构和 Ubuntu 22.04；Windows 另以实际 v142／14.29 工具集运行本机兼容配置。所有配置统一使用 Qt 6.8.2，不将宿主的 Visual Studio 名称当作编译器版本。Linux 使用 Xvfb 虚拟显示，其他平台使用 CI 桌面环境。稳定的 `Desktop admission` 汇总检查仅在所有矩阵任务成功时通过，失败、取消和跳过均不算通过；原有必需检查继续保留。运行日志、配置／工具链身份、源文件摘要和验证窗口自身截图保存为七天有效的诊断工件。

桌面 CTest 同时执行 `desktop_admission`、`file_workflow` 与 `standalone_visual`，分别保留 QtTest 报告。文件测试包含自建真实文件的保存竞争和失败恢复、实际独立窗口交互、关闭确认及第二进程路由；视觉测试覆盖明暗与六种强调色、共享尺寸、Tab 焦点、反馈、正文缩放和阅读位置，并以独立子进程核对 1／1.5／2 倍采样。缺少任一报告或出现 Qt 严重诊断均失败。窗口截图和测量只作为该次运行证据，不修改设计原稿。

Qt 获取和第三方 Action 是 CI 工具输入，固定 Action 提交及版本；失败不通过更换断言或把缺失测试视为成功。CI 不打包、签名、发布或安装产品，不配置系统文件关联。跨平台自动化及虚拟显示测试不等于真实输入法、屏幕阅读器、文件管理器、物理显示设备或人工视觉验收；单文件功能原型通过也不等于主工作区、完整主题、资源管理或全部编辑器准入完成。

当前构建主机显式使用 `ubuntu-24.04`、`windows-2022`、`macos-15-intel`（x86_64）和 `macos-15`（arm64）；Qt 文档试验另覆盖最低 Linux 参考环境 `ubuntu-22.04`。macOS 标签按 [GitHub 镜像表](https://github.com/actions/runner-images#available-images)区分架构，不使用已进入退役停机的 macOS 14 镜像。主机升级不提高[产品最低系统目标](platform-support.md)，输出架构与最低运行环境仍按实际证据分别核验。

设计原稿、提示词、可编辑素材和必要的实验源码保留；导出 ZIP、运行截图、报告、缓存及各层级 `dist/` 不进入源码。临时 CI 工件可按需设置有效期，不当作发布包。
